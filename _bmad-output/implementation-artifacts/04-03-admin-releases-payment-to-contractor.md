## 📋 User Story

**As an** admin,  
**I want to** release an approved milestone's payment to the contractor,  
**so that** the contractor receives their earned funds.

### Payment Release Action

- [ ] **Validation before call:**
  - Call `canTransition('payment', 'ready_for_payout', 'paid_out')` from `utils/statusMachine.ts`
  - If false, show error toast and return (don't call API)
- [ ] **Optimistic update:**
  - Immediately set payment status to `paid_out` in Pinia store
  - Close dialog
  - Show loading toast (brief message while request completes)
- [ ] **API call:** `POST /payments/:id/release`
  - Use `useFetch` or `$fetch` through API wrapper
  - Parameter: milestone/payment ID (from milestone object)
  - Expected response: `{ data: { id, status: "paid_out", ... }, message: "..." }`
- [ ] **On success:**
  - Payment status now shows as `paid_out` (badge color updates)
  - "Release payment" button disappears (hidden in view)
  - Success toast: "Payment released — [amount]" (i18n: `payment.message.released`)
  - Optional: in-app notification sent to contractor (if notification system available)
    - Message: "Payment released — SAR 50,000" (auto-generated by backend)
- [ ] **On error:**
  - Revert payment status to `ready_for_payout` (rollback in store)
  - Show error toast with backend message or generic "Release failed"
  - Dialog remains open (user can try again or close)
  - Do NOT proceed with action on partial failures

### Architecture & Patterns

**Payment Release Flow — State Machine:**

```
milestone.status: approved
payment.status: ready_for_payout
                    ↓ [admin clicks Release]
                    ↓ [canTransition check]
                    ↓ [optimistic update]
                    ↓ [POST /payments/:id/release]
payment.status: paid_out (on success)
or
payment.status: ready_for_payout (on error — rollback)
```

**Key patterns from previous stories:**

- **Optimistic updates:** Set state immediately, rollback on error (from 04-01, 03-05)
- **Permission checks:** Use `usePermission().can()` for visibility (from 04-02)
- **Derived payment status:** Use `derivePaymentStatus()` to show badge (from 04-02)
- **Error handling:** Display user-friendly error messages via toast (from previous stories)

### Composable Update: `useMilestones.ts`

**Add new action:**
```typescript
async function releaseMilestonePayment(milestoneId: string) {
  try {
    // Validate transition before optimistic update
    const milestone = getById(milestoneId)
    const paymentStatus = derivePaymentStatus(milestone.status)
    
    if (!canTransition('payment', paymentStatus, 'paid_out')) {
      notify.error(t('errors.invalid_transition'))
      return
    }

    // Optimistic update
    const prev = milestone.status
    setStatus(milestoneId, milestone.status) // milestone.status doesn't change
    // Payment status is derived, so it auto-updates visually

    // API call
    const response = await useApi(`/payments/${milestoneId}/release`, {
      method: 'POST'
    })

    // Success
    notify.success(t('payment.message.released', {
      amount: formatCurrency(milestone.amount)
    }))

  } catch (error) {
    // Rollback — fetch fresh state from server
    await fetchMilestoneDetail(milestoneId)
    notify.error(error.message || t('errors.release_failed'))
  }
}
```

### API Contract

**Endpoint:** `POST /payments/:id/release`

**Path parameter:**
- `id`: milestone/payment ID (string UUID)

**Request body:**
- None (can be empty `{}`)

**Success response (200):**
```json
{
  "data": {
    "id": "uuid",
    "milestone_id": "uuid",
    "status": "paid_out",
    "amount": 50000,
    "released_at": "2026-05-08T15:30:00Z"
  },
  "message": "Payment released successfully"
}
```

**Error responses:**
- `400 Bad Request` — Invalid milestone ID or status
- `403 Forbidden` — User not admin
- `404 Not Found` — Payment not found
- `422 Unprocessable Entity` — Invalid state transition (e.g., payment already paid_out)
- `500 Internal Server Error` — Unexpected error

## 💡 Implementation Notes

### Key Implementation Decisions

1. **Optimistic update pattern**
   - Set state immediately on confirm (better UX)
   - Rollback on API error by re-fetching from server
   - Prevents double-click issues with button disabled during request

2. **No-undo warning is critical**
   - This is irreversible (backend confirms)
   - Amber warning banner with clear message
   - User must click through confirmation
   - No double-confirm needed (single dialog is sufficient)

3. **Payment status derived, not stored**
   - Release doesn't change milestone.status
   - Payment status auto-updates via `derivePaymentStatus()`
   - No separate API for payment state transition

4. **Admin-only, no conditional release**
   - Only admins release payments
   - Only on `approved` milestones
   - No cascading releases or bulk actions

### Common Mistakes to Avoid

❌ **Do NOT** assume payment is stored separately in API  
✅ **DO** understand payment status is derived from milestone status

❌ **Do NOT** show this button to contractors or clients  
✅ **DO** check `can('release_payment')` — only admin/super_admin

❌ **Do NOT** skip `canTransition()` validation  
✅ **DO** validate state transition before API call

❌ **Do NOT** use hardcoded colors or label text  
✅ **DO** use `PAYMENT_STATUS_META` for consistency

❌ **Do NOT** make release action synchronous  
✅ **DO** use async/await with try/catch and proper rollback
