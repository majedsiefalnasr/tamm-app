# BMAD Method — Cheat Sheet
### TAMM Frontend Team · Claude Code + VSCode · v6

> **BMAD** = Breakthrough Method for Agile AI-Driven Development
> An open-source framework that replaces chaotic "vibe coding" with a structured,
> persona-driven workflow across the full software development lifecycle.
> Every decision has an owner. Every phase has a gate. Every story has a definition of done.

---

## The core idea in one sentence

Instead of talking to a generic AI assistant, you work with **specialized agent personas** —
each with a distinct role, mindset, and set of outputs —
and hand off structured artifacts between them, just like a real agile team.

---

## The 4 phases — always in this order

```
Phase 1: Analysis       → understand the problem
Phase 2: Planning       → define what to build
Phase 3: Solutioning    → design how to build it
Phase 4: Implementation → build it, story by story
```

**TAMM status:** Phases 1–3 are already done.
We have all planning docs. We start directly at Phase 4.
`bmad/config.yaml` marks phases 1–3 as `skip`.

## The agents — who does what

BMAD v6 (BMM module) has **8 specialized agents**. Each is an `.md` file
inside `_bmad/bmm/agents/`, surfaced as slash commands in Claude Code.

| Agent | Name | Slash command | Key outputs |
|---|---|---|---|
| Analyst | Mary | `/product-brief` | `project-brief.md` |
| PM | John | `/prd` | `prd.md`, epics |
| UX Designer | Sally | — | `ux-spec.md`, user flows |
| Architect | Winston | `/architecture` | `architecture.md` |
| Scrum Master | Bob | `/create-story` | `story-[slug].md` files |
| Developer | Amelia | `/dev-story` | Working code |
| QA | Quinn | — | Test files, e2e tests |
| PO | — | `/solutioning-gate-check` | Checklist validation |

**Quick rule:**
Deciding *what* to build → PM (`/prd`)
Breaking it into tasks → SM (`/create-story`)
Building it → Dev (`/dev-story story-slug`)
Writing tests → QA

## v6 directory structure — what `npx bmad-method install` creates

```
your-project/
├── _bmad/                    ← BMAD runtime (agents, workflows, tasks)
│   ├── core/                 ← core skills (bmad-help, etc.)
│   ├── bmm/                  ← BMad Method module
│   │   ├── agents/           ← pm.md, dev.md, sm.md, architect.md...
│   │   ├── workflows/        ← sharded workflow step files
│   │   └── config.yaml       ← BMM module settings + dev_load_always_files
│   ├── config.toml           ← central BMAD configuration (TOML)
│   ├── custom/               ← your TOML overrides (survives updates)
│   └── _config/
│       ├── manifest.yaml     ← tracks installed versions
│       └── agent-manifest.csv
├── _bmad-output/             ← AI writes planning artifacts here
│   └── (PRDs, arch docs, etc. if generated by BMAD)
├── bmad/                     ← project-specific config (created by /workflow-init)
│   └── config.yaml           ← project name, level, paths, phase settings
└── .claude/
    └── commands/             ← slash command stubs (auto-created)
        ├── create-story.md
        ├── dev-story.md
        ├── workflow-init.md
        └── ...
```

**Key distinction:**
- `_bmad/` = BMAD's code — agents and workflows. Don't edit manually.
- `bmad/` = your project config — created by `/workflow-init`. Edit freely.
- `_bmad-output/` = where BMAD writes generated docs. We use `docs/` instead (configured in `bmad/config.yaml`).

```bash
# Install BMAD v6 into your project root
npx bmad-method install

# During install, select:

# - IDE: claude-code
```

## The most important config — `_bmad/bmm/config.yaml`

The `dev_load_always_files` key makes every `@dev` (Amelia) session
automatically load TAMM's rules without you repeating them:

```yaml
# _bmad/bmm/config.yaml — add this section
dev_load_always_files:
  - CLAUDE.md
  - docs/coding-standards.md
  - docs/status-flows.md
  - docs/api-contracts.md
```

Every `/dev-story` session reads these four files automatically.
Amelia knows TAMM's stack, rules, state machine, and API state from the first message.

## The TAMM workflow — exactly how to run it

TAMM skips phases 1–3. We start at Phase 4.

### What we have already ✅

| BMAD artifact | TAMM equivalent | Location |
|---|---|---|
| `project-brief.md` | MVP decisions + system overview | Source project docs |
| `prd.md` | MVP Scope + User Roles | Source project docs |
| `architecture.md` | `CLAUDE.md` + `coding-standards.md` | project root + `docs/` |
| `ux-spec.md` | `frontend-spec.md` | `docs/` |
| Status & state docs | `status-flows.md` | `docs/` |
| API contract | `api-contracts.md` | `docs/` |
| Epic files | `epic-01` through `epic-06` | `docs/stories/` |

### Sprint workflow — repeat every sprint

```
Day 1 of sprint:
  /solutioning-gate-check     ← PO validates all docs are consistent
  /create-story               ← SM generates story files from next epic
  Review + approve stories together (both devs)

Days 2–N of sprint:
  Dev A: /dev-story story-[slug]   ← implements story
  Dev B: /dev-story story-[slug]   ← implements story in parallel
  QA:    "Act as @qa, generate tests for story-[slug]"

End of sprint:
  All stories complete + tests passing
  Merge feat/track-a and feat/track-b to develop
  /workflow-status → confirm sprint done
```

## The Dev agent — lean context discipline

`/dev-story` loads Amelia with only what she needs:

```
story file                ← what to build (acceptance criteria)
+ dev_load_always_files   ← how to build it (TAMM rules)
= everything needed, nothing extra
```

Do not paste extra context into the chat. If Amelia needs something, it should be in one of the four always-load files or the story file. If it's not there, add it to the right doc — don't fix it in the chat.

### How to run a dev session

```
/dev-story story-auth-login

Amelia reads the story + CLAUDE.md + coding-standards.md + status-flows.md + api-contracts.md

She presents her implementation plan.
You approve the plan.
She builds exactly what the story says — nothing more.
```

**Always approve the plan before she codes.** This enforces `CLAUDE.md §0.4`.

## Story file structure — what `/create-story` generates

```markdown
# Story: [ID] — [Title]

## Status: draft | ready | in-progress | complete

## Context
Why this story exists. Which epic. What previous story delivered.

## Goal
One sentence: what does "done" look like?

## Acceptance criteria
- [ ] Specific, testable criterion 1
- [ ] RTL verified
- [ ] TypeScript clean — no errors, no `any`
- [ ] No console errors

## Technical notes
- Composable to create/use
- Store to update
- Endpoint (or mock path if not available)
- Components to build

## Out of scope
What this story explicitly does NOT cover.

## Dependencies
- Requires: story-[previous-slug] to be complete
- Blocked by: endpoint GET /projects/:id (use mock until available)
```

## Party Mode — multi-agent discussion

Use when a decision needs multiple perspectives before building:

```
Party Mode: @pm @architect @ux-designer

Discussion: Should milestone rejection require a mandatory reason field?
Each agent give your perspective, then reach a recommendation.
```

Use for decisions. Never for implementation.

## When to use which command

| Situation | Command |
|---|---|
| Unsure what to do next | `/bmad-help` |
| Starting a new sprint | `/create-story` (SM) |
| Ready to implement a story | `/dev-story story-[slug]` |
| Need tests for a story | Ask `@qa` directly |
| Docs feel inconsistent | `/solutioning-gate-check` (PO) |
| New unplanned feature arrives | `/product-brief` → `/prd` → `/create-story` |
| Architecture decision needed | Ask `@architect` directly |
| Multi-perspective debate | Party Mode |
| Check project health | `/workflow-status` |

---

## What NOT to do

| Don't | Do instead |
|---|---|
| `/dev-story` without a story file existing | `/create-story` first |
| Let Dev read everything on every task | Use `dev_load_always_files` — lean context |
| Generate all stories at once | Approve 2–3 at a time from `/create-story` |
| Skip `/solutioning-gate-check` at sprint start | Always gate before sprint starts |
| Give Dev vague instructions | Give Dev a story file with exact criteria |
| Manually edit files inside `_bmad/` | Use `_bmad/custom/` TOML overrides instead |
| Use `@dev` for architecture decisions | Use `@architect` or Party Mode |
| Run `/dev-story` without approving the plan first | Always approve plan before code |

## BMAD complexity levels — where TAMM fits

| Level | Project type | Stories | Phase requirements |
|---|---|---|---|
| 0 | Single atomic change | 1 | Skip to Dev |
| 1 | Small feature | 1–10 | Tech spec only |
| 2 | Medium feature set | 5–15 | PRD + Architecture |
| **3** | **Complex integration** | **12–40** | **Full workflow** ← TAMM |
| 4 | Enterprise expansion | 40+ | Full workflow + modules |

TAMM is **Level 3**. All phases apply. No shortcuts.
