# BMAD Method — Cheat Sheet
### TAMM Frontend Team · Claude Code · v6.6.0

> **BMAD** = Breakthrough Method for Agile AI-Driven Development
> A structured, persona-driven workflow across the full software development lifecycle.
> Every decision has an owner. Every phase has a gate. Every story has a definition of done.

---

## The core idea in one sentence

Instead of talking to a generic AI assistant, you work with **specialized agent personas** —
each with a distinct role, mindset, and set of outputs —
and hand off structured artifacts between them, just like a real agile team.

---

## The 4 phases — always in this order

```
Phase 1: Analysis       → understand the problem
Phase 2: Planning       → define what to build
Phase 3: Solutioning    → design how to build it
Phase 4: Implementation → build it, story by story
```

**TAMM status:** Phases 1–3 are already complete.
All planning docs exist. We start directly at **Phase 4**.

## The key agents (BMM module)

| Agent | Slash command | When to use |
|---|---|---|
| **SM** (Scrum Master) | `/bmad-create-story` | Break an epic into individual story files |
| **Dev** | `/bmad-dev-story` | Implement a specific story |
| **Code Review** | `/bmad-code-review` | Review code after dev completes a story |
| **QA** | `/bmad-qa-generate-e2e-tests` | Generate automated tests for implemented code |
| **Sprint Planning** | `/bmad-sprint-planning` | Plan the sprint before stories begin |
| **Sprint Status** | `/bmad-sprint-status` | Check current sprint progress at any time |

**Quick rule:**
- Breaking epics into tasks → SM (`/bmad-create-story`)
- Building a story → Dev (`/bmad-dev-story`)
- Reviewing code → CR (`/bmad-code-review`)
- Writing tests → QA (`/bmad-qa-generate-e2e-tests`)
- Stuck or unsure → `/bmad-help`

## The TAMM workflow — exactly how to run a sprint

### What we already have ✅

| BMAD artifact | TAMM equivalent | Location |
|---|---|---|
| Product brief | MVP decisions + system overview | `CLAUDE.md` |
| PRD | 8 epics with all stories | `_bmad-output/planning-artifacts/` |
| Architecture | Stack decisions + rules | `CLAUDE.md` + `docs/coding-standards.md` |
| UX spec | Design system | `docs/frontend-spec.md` |
| State machine | Status flows | `docs/status-flows.md` |
| API contract | All endpoints | `docs/api-contracts.md` |
| Build order | Phase + branch plan | `docs/build-order.md` |

### Sprint cycle — repeat every sprint

```
Sprint start:
  /bmad-sprint-planning        ← produces sprint plan
  /bmad-create-story           ← SM shards next epic into story files
  Review + approve stories (both devs together)

During sprint (parallel):
  Dev A: /bmad-dev-story [story-file-path]
  Dev B: /bmad-dev-story [story-file-path]

After each story:
  /bmad-code-review            ← review the implementation
  /bmad-qa-generate-e2e-tests  ← generate tests

Sprint end:
  /bmad-sprint-status          ← confirm all stories complete
  /bmad-retrospective          ← optional, recommended at epic boundaries
  Merge feature branches to develop
```

## Running a dev session — step by step

```
1. Check what's next:
   /bmad-sprint-status

2. Generate a story file (if not done yet):
   /bmad-create-story
   → specify: source epic path, output to _bmad-output/implementation-artifacts/

3. Implement the story:
   /bmad-dev-story
   → paste or reference the story file path

4. Dev presents implementation plan — APPROVE THE PLAN before any code is written
   (this enforces CLAUDE.md §0.4 — define success before starting)

5. Dev builds. Review the diff when done.

6. Review the code:
   /bmad-code-review

7. Generate tests:
   /bmad-qa-generate-e2e-tests
```

**Never skip step 4.** Approving the plan is the most important gate.

## Story file format — what `/bmad-create-story` generates

```markdown
# Story: [ID] — [Title]

## Status: draft | ready | in-progress | complete

## Context
Why this story exists. Which epic. What the previous story delivered.

## Goal
One sentence: what does "done" look like?

## Acceptance criteria
- [ ] Specific, testable criterion
- [ ] RTL verified in Arabic
- [ ] TypeScript clean — no errors, no `any`
- [ ] No console errors or warnings

## Technical notes
- Composable to create/use
- Store to update
- Endpoint (or mock path if not yet available)
- Components to build

## Out of scope
What this story explicitly does NOT cover.

## Dependencies
- Requires: [previous story slug] to be complete
- Blocked by: [endpoint] — use mock at [mock path] until available
```

## Party Mode — multi-agent discussion

Use when a decision needs multiple perspectives before building:

```
/bmad-party-mode

Topic: Should milestone rejection require a mandatory reason field?

Participants: PM, Architect, UX Designer
Each agent give your perspective, then reach a consensus.
```

Use for **decisions**. Never for implementation.

---

## What NOT to do

| Don't | Do instead |
|---|---|
| `/bmad-dev-story` without a story file | `/bmad-create-story` first |
| Skip plan approval before coding | Always approve plan before code |
| Generate all story files at once | 2–3 at a time, review before continuing |
| Edit files inside `_bmad/` directly | Use `_bmad/custom/` TOML overrides |
| Use Dev agent for architecture decisions | Use `/bmad-party-mode` |
| Paste TAMM rules into chat | They auto-load via `project_knowledge` in config |

## BMAD complexity levels — where TAMM fits

| Level | Project type | Stories | Requirements |
|---|---|---|---|
| 0 | Single atomic change | 1 | Skip to dev |
| 1 | Small feature | 1–10 | Tech spec only |
| 2 | Medium feature set | 5–15 | PRD + Architecture |
| **3** | **Complex integration** | **12–40** | **Full workflow ← TAMM** |
| 4 | Enterprise expansion | 40+ | Full workflow + modules |

TAMM is **Level 3** — 40 stories across 8 epics. Full workflow applies.
